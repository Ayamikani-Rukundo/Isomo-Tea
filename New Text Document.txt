# 3. PRODUCT VISION

Isomo Tea is an anonymous messaging platform exclusively for the Isomo Academy community.

The purpose is to create a comfortable, playful environment where scholars can communicate, joke, discuss, gossip, share ideas, and express themselves without exposing their real-world identities to other members.

The platform has three central experiences:

1. General Tea — the central community conversation.
2. Private Inbox — anonymous one-to-one conversations.
3. Admin Control — membership, content and application management.

The product must feel modern, distinctive, fast, and enjoyable.

It should not look like a generic messaging template.

# 5. AUTHENTICATION AND ACCOUNTS

Ordinary scholars should register using:

- Anonymous username.
- Password.
- Isomo access code.

They should not need to provide their real names, email addresses, or phone numbers.

### Username system

- One account per scholar.
- One anonymous username per account.
- Usernames must be unique.
- Username comparisons must be case-insensitive.
- Users can change their username later.
- Claimed usernames disappear from suggestions.
- Users can select from suggested usernames or create their own.
- Use creative, playful, unusual username suggestions.
- Never use actual scholar identities in the suggestions.

### Isomo access code

The developer should be able to configure and change the access code.

The code must be validated securely on the backend.

Do not expose it in frontend source code.

Scholars should enter the code directly when registering. Do not implement an administrator approval-request system.

### Authentication security

Use Supabase Authentication appropriately.

Never store plaintext passwords.

Implement a secure username-to-authentication-account lookup without exposing other users' private authentication details.

Maintain sessions across browser and Android application restarts.

# 8. MEDIA AND VIEW-ONCE FUNCTIONALITY

Implement:

- View-once images.
- Listen-once audio.
- View-once videos.

Each recipient should only be able to access the media once through the application.

### General-chat videos

General-chat videos are intended for all eligible members.

When a video is sent:

1. Upload the actual video to Supabase Storage.
2. Store its metadata in PostgreSQL.
3. Record all eligible recipients.
4. Track individual viewing status.
5. Allow each eligible member one viewing opportunity.
6. When everyone has viewed it, permanently delete the storage object and associated database records.

If some recipients never view the video, automatically expire and clean it up after a configurable period.

Use secure backend cleanup functionality.

Do not store actual media files inside PostgreSQL.

Respect Supabase storage, bandwidth and upload constraints.

Do not claim to prevent external screen recording or screenshots.
